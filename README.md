## 一、背景与目标

### 1.1 Microduck 是什么

**Microduck** 是 Hugging Face 与 Pollen Robotics 联合推出的开源双足机器人——一只 25 厘米高、约 800 克重的"机械鸭"，售价 399 美元：

- **15 个电机**分布在腿、躯干、头部和喙
- 喙可以开合，能当夹爪用，能叼起约 800 克物体
- 传感器齐全：广角摄像头、LiDAR、双 IMU、麦克风、扬声器、NFC、Wi-Fi、蓝牙
- **出厂自带 7 种行为**：走路、下蹲、坐下、跌倒恢复、踢球、叼取、轮滑

但比硬件更有意思的是它的**软件哲学**——整套强化学习训练栈完全开源（Apache-2.0），可以自己训练新技能：

> 在仿真里学（MuJoCo + PPO），训练好了再部署到真机上跑（50Hz）。

它的官方训练仓库 [`pollen-robotics/microduck_rl`](https://github.com/pollen-robotics/microduck_rl) 就是我们要用的主角。

### 1.2 本文目标

**最小目标**：在云 GPU 上训练一个"平地走路"策略，并**亲眼看到鸭子走起来**。

**最终效果参照**：官方有一个浏览器沙盒（Microduck Sandbox），打开网页就能玩鸭子——MuJoCo 物理引擎编译成 WebAssembly、策略网络用 `onnxruntime-web` 跑，**全部在浏览器标签页内执行，不需要 GPU、不需要服务器推理**。

> ### 🎯 官方沙盒地址（本文的目标效果）
>
> **<https://huggingface.co/spaces/pollen-robotics/microduck-simulator>**
>
> 建议现在就可以打开看一眼**后面亲手复现出这个网页里那只走得稳稳的鸭子。**

**预期时间成本**：装环境 15–30 分钟，训练 1–2 小时，全程约 2 小时。

## 二、知识点速通

看不懂下面这几个词，后面的命令就是天书。建议花 3 分钟过一遍。

### 2.1 强化学习（RL）与 PPO

**强化学习**的本质是"试错学习"：机器人不断尝试动作，做对了给奖励，做错了扣分，慢慢就学会了。

Microduck 用的是 **PPO（近端策略优化）**，由 `leggedrobotics/rsl_rl` 实现。PPO 的特点是**更新保守**——每次只小步调整策略，避免"一步走错满盘皆输"。核心参数 `clip_param=0.2` 就是限制每次更新的幅度。

### 2.2 并行环境：为什么是 4096

强化学习需要**海量**试错数据。如果一次只跑一个机器人，训练要花几个月。

所以框架会**同时开几千个仿真环境**——4096 个鸭子同时在不同场景里摔跤，一秒钟积累的数据量顶单机跑一周。这也是为什么必须用 GPU：**MuJoCo Warp 把这些并行物理仿真全部搬到 GPU 上跑**。

> 💡 4096 个并行环境只占约 6GB 显存，所以 L40S / 4090 都绰绰有余。

### 2.3 Sim2Real 与"域随机化"

在仿真里走得再好，搬到真机上也可能秒摔——这就是著名的 **Sim2Real Gap**。

Microduck 的解法是**域随机化（Domain Randomization）**：训练时故意随机扰动摩擦系数、电机延迟、电池电压、质心位置等参数，让策略学会在"不完美的世界"里保持平衡，而不是过拟合到仿真的理想参数。

### 2.4 观测-动作契约：61 维 → 14 维

新版策略的输入输出是**固定契约**：

```
输入（actor）：61 维
  ├─ IMU（角速度、重力方向）
  ├─ 关节位置 / 速度
  ├─ 历史动作
  └─ 命令：twist 速度(3) + 头部姿态(4) + 身体姿态(6) = 13 维

输出（action）：14 维关节目标角度
```

**为什么是"目标角度"而不是力矩？** 因为真机上舵机就是这么控制的——**控制方式与真机对齐，是缩小 Sim2Real 差距的关键一招**。

### 2.5 课程学习：先学站，再学走

训练不是一上来就要求走。**Curriculum（课程学习）** 会循序渐进：

- 开局只有 2% 的环境在练"站立"（`Curriculum/standing_envs: 0.02`）
- 站得稳了，才逐步放宽速度命令、加大难度
- 罚项权重也是分段加大，避免初期就把策略"罚"到不敢动

理解这一点很重要——**后面看到 reward 波动，你就不会慌了**。第四章会用数据说明这一点到底有多重要。

**选型要点：**

|     |                     |                                       |
| 镜像  | MuJoCo 物理引擎镜像       | 已预装 Ubuntu 22.04 + CUDA 12.8 + MuJoCo |
| 数据盘 | **50GB**            | 训练环境约 8GB + checkpoint + 日志           |

> ⚠️ **踩坑提醒 #1**：如果图省事选了 A100 的话，你会发现能训练但看不到鸭子——渲染不了。这个坑很隐蔽，因为训练日志一切正常。

### 3.1 一个现实问题：原来的"傻瓜镜像"没了

网上流传最广的一篇 Microduck 教程，是基于算力自由平台一个**内置封装镜像**的——镜像里已经把环境装好、路径固定好，还有一套中文命令（`bash duck train 平地行走`），堪称"傻瓜套餐"。

**但我动手时发现：那个镜像已经下架了。**

这其实是个很典型的教训——

> 💡 **经验 #1：优先依赖"上游官方源码"，而不是"第三方封装"**
>
> 第三方封装好用，但它随时可能下架、失联、不再维护。  
> 官方 GitHub 仓库才是**永远可用**的源头。  
> 遇到封装失效时，正确的姿势是：**回到官方仓库，自己走一遍标准流程**。

于是路线调整为：**用官方 `microduck_rl` 仓库 + 自己写一键脚本**，效果一样，而且不依赖任何第三方。

### 3.2 环境安装

登录实例后（SSH 或 JupyterLab 终端都行），核心就四步：

```bash
# 1. 在数据盘建工作目录（系统盘只有 30GB，放不下 8GB 环境）
export WORKSPACE=/root/gpufree-data/microduck
export UV_CACHE_DIR=/root/gpufree-data/.cache/uv
mkdir -p "$WORKSPACE" "$UV_CACHE_DIR"
cd "$WORKSPACE"

# 2. 安装 uv（Python 包管理器，仓库用它锁定依赖）
curl -LsSf https://astral.sh/uv/install.sh | sh
source "$HOME/.local/bin/env"

# 3. 拉取官方源码
git clone https://github.com/pollen-robotics/microduck_rl.git
cd microduck_rl

# 4. 安装依赖（首次约 15~30 分钟，共 142 个包）
uv sync
```

> ⚠️ **踩坑提醒 #2**：`uv sync` 会下载约 8GB 依赖，国内网络可能较慢。  
> 如果卡住不动，可以配置国内镜像源加速，或耐心等待——**别中断**，中断了要从头下。

### 3.3 关键一步：先烟测，别急着训练

这是官方维护者在 `AGENTS.md` 里**反复强调**的：

```bash
# 64 个并行环境，只跑 5 轮迭代
uv run train Mjlab-Velocity-Flat-MicroDuck \
  --env.scene.num-envs 64 \
  --agent.max_iterations 5
```

**烟测要证明的是**（不是证明鸭子会走）：

- ✅ MuJoCo Warp 能在 CUDA 上创建并行环境
- ✅ 观测/动作维度与模型一致
- ✅ 奖励计算没有 NaN
- ✅ checkpoint 能正常写入磁盘

看到 Actor 是 `61 → 512 → 256 → 128 → 14`、Critic 是 `76 → ... → 1`，就说明模型契约正确。

> 💡 **经验 #2：先跑通链路，再追求效果**
>
> 很多人一上来就开 4096 环境长训，跑到一半才发现 CUDA 版本不匹配、路径写错——白白浪费几小时 GPU 费。  
> **5 分钟烟测，能省你 2 小时。**

### 3.4 正式开始训练

确认烟测通过后，启动正式训练：

```bash
# 后台运行，日志写入文件，防止断线中断
nohup uv run train Mjlab-Velocity-Flat-MicroDuck \
  --env.scene.num-envs 4096 \
  --agent.max_iterations 6000 \
  > /root/gpufree-data/train.log 2>&1 &

# 实时查看进度
tail -f /root/gpufree-data/train.log
```

**训练过程中，你只需要盯三个指标：**

| 指标                              | 含义         | 健康趋势 |
| ------------------------------- | ---------- | ---- |
| `Mean reward`                   | 平均奖励，越高越会走 | 持续上升 |
| `Mean episode length`           | 每回合存活步数    | 持续上升 |
| `Episode_Termination/fell_over` | 摔倒计数       | 持续下降 |

**我的真实训练曲线：**

| 时间点           | reward     | 存活步数 | fell_over 计数* |
| ------------- | ---------- | ---- | ------------- |
| 20 轮          | 0.30       | 36   | 2.38          |
| 203 轮（5 分钟）   | **96.03**  | 889  | 1.00          |
| 833 轮（21 分钟）  | **112.27** | 952  | **0.29**      |
| 3305 轮（12:59） | 110.70     | 954  | 0.42          |
| 5245 轮（13:47） | **117.91** | 969  | 0.42          |
| 5781 轮（14:00） | 113.05     | 964  | 0.42          |
| 5999 轮（训练结束）  | **116.81** | 966  | 0.42          |

> \* 注意：`fell_over` 这一列是**摔倒的环境个数**，不是百分比。我一开始把它误读成"摔倒率 41.67%"，后来读了源码才发现口径不对——它要和超时计数（`time_out`）相比才有意义：末次迭代两者之比是 5 : 49，即**约 9.3% 的回合以摔倒告终，90.7% 是活满 20 秒被计时器正常结束**。详见 4.2 节。

几点观察：

1. **前 200 轮是"质变期"**：从完全不会走（reward 0.30）到基本会走（96.03），只用了 5 分钟。这符合课程学习的节奏——先学会站，再学会走。
2. **之后是漫长的"精修期"**：reward 从 96 慢慢爬到 117 左右，涨幅不大但存活步数一路涨到 966 步（接近单回合上限）。鸭子已经不是"会走"，而是"走得稳"。
3. **后期 reward 会小幅波动，不要慌**：5781 轮时回落到 113，最终又回到 116.81。PPO 自适应学习率本来就带波动，只要存活步数稳定在高位，策略就是健康的。

> 🎉 **最终成绩：训练 2 小时 26 分钟跑满 6000 轮，产出 25 个 checkpoint（正式 run），最新权重 model_5999.pt。**
>
> 这个速度其实很惊人：前 200 轮基本是"从完全不会到会走"的质变期，剩下 95% 的时间都在把"会走"打磨成"走得稳"。

### 3.6 训练完的产物

训练完成后，你会得到：

- **每 250 轮自动存一个 checkpoint**（`model_*.pt`）——6000 轮正式训练共 **25 个**（`model_0` 到 `model_5999`），随时可以回放任意阶段
- **导出的 ONNX 策略**——可以直接部署到真机，或塞进浏览器沙盒
- **TensorBoard / W\&B 日志**——完整的训练曲线

> 💡 小技巧：**不同 checkpoint 回放对比着看**特别有成就感——早期 checkpoint 还在原地抽搐，中期能走但踉踉跄跄，后期的已经步伐稳健。策略的成长过程一目了然。

### 4.2 它真的学会了吗：两条最有说服力的曲线

reward 涨了不稀奇，稀奇的是**行为的性质变了**。先看每回合能活多久：

![回合存活步数：从 36 步涨到 966 步](./images/charts/02_episode_length.png)

*回合上限 1000 步（20 秒 @ 50Hz）。开局平均只能活 36 步（0.7 秒），最好的一次在第 5290 轮达到 997 步，末段稳定在 966 步——活满了 96.6% 的回合时长。*

再看"回合是怎么结束的"：

![摔倒占回合结束原因的比例：从 84% 降到 9%](./images/charts/03_fall_rate_flip.png)

*摔倒占全部回合结束原因的比例。早期约 84% 的回合以摔倒告终，末期降到约 9%。*

为什么这条曲线比 reward 更有说服力：它衡量的不是"分数"，而是**行为的性质变了**——从"走几步就摔"（失败），变成"走满 20 秒被计时器请下场"（成功）。这是一个从失败到成功的性质转换，不是数值的连续爬升。

另外两条"零"也值得记一笔：`nan_state`（物理数值爆炸）和 `out_of_terrain_bounds`（跑出地形）**全程为 0**——框架的 NaN 防护确实在工作，平地任务也没有边界问题。

### 4.3 reward 会"骗人"：分数下降，能力上升

如果你一直盯着 reward，会在中途看到吓人的一幕：

![Mean reward 曲线：峰值 125.05 出现在第 974 轮，终点回落到 116.81](./images/charts/01_reward_total.png)

*每 20 轮取均值。峰值 125.05 出现在第 974 轮，终点是 116.81——分数是从高处回落下来的。*

**分数在 974 轮达到最高，之后一路回落**。这是训坏了吗？不是。原因在课程的节奏里：

![七条课程各自的难度爬升窗口](./images/charts/06_curriculum.png)


*7 条课程各自的爬升窗口。紫点标出该课程开始生效与爬升结束的轮次，右侧是初值 → 终值。*

**所有难度都在前 2000 轮就加完了**：动作平滑惩罚和头部偏置惩罚第 1500 轮升满，头部指令范围与站桩环境第 2000 轮到位，之后 4000 轮难度封顶不再变化。

也就是说，974 轮之后它面对的题目**还在持续加难**（同一能力自然拿不到同样高的分），而到 2000 轮后难度固定、剩下 4000 轮是纯精修。总分从 125 回落到 117，就是"难度加码"与"能力精修"两股力量叠加后的净结果。

> 💡 **经验 #4：reward 不能当成绩单用**
>
> 分数下降和能力提升可以**同时发生**。复盘 RL 训练时，先看分项和"存活/摔倒"这类行为指标，再看总分——这个顺序不能反。

### 4.4 16 项奖励，谁在真正起作用

配置里写了 16 项奖励，是不是每项都在起作用？把末次迭代（第 5999 轮）每项的实际得分贡献拆开看：

![16 项奖励的每回合得分贡献](./images/charts/07_reward_contrib.png)

*末次迭代 16 项奖励的每回合得分贡献，合计正好等于 Mean reward 116.81。*

三个发现：

**1. 四大主力贡献了几乎全部分数**：`upright`（保持直立，+30.3%）、`head_pose_tracking`（头部姿态跟踪，+29.5%）、`track_linear_velocity`（线速度跟踪，+22.1%）、`air_time`（腾空时长，+18.6%）。最终策略几乎完全是被这四项塑造的。

**2. 反直觉：教"摆头"的分数比教"走路"还多**（29.5% vs 22.1%）。这不是巧合——配置里 `head_pose_tracking` 的权重就是 2.0，和 `track_linear_velocity` 一样大。这次训练有近三成的信号在教它按指令摆头（Microduck 的招牌交互能力）。**如果你只想要"走得准"，这两个权重需要重新配比。**

**3. 有 8 项几乎完全不起作用**：`angular_momentum` 和 `body_pose_tracking` 贡献恰好为 0，`foot_slip`、`self_collisions`、`foot_swing_height`、`foot_clearance`、`dof_pos_limits` 的贡献都不到 0.15%。它们在配置里明明写着权重，但对最终策略几乎没有塑造力。

但注意——**"贡献小"不等于"可以删"**：`body_pose_tracking` 权重为 0 是刻意设计（基础设施保留但禁用，只为保住观测槽）；而 `angular_momentum` 这类小权重的角色更像"保险丝"——只要不爆表就不产生梯度。判断该不该删需要做消融实验（去掉重训一次），单次训练的数据给不出这个结论。

###

### 4.6 结论：已经收敛

取第 4000~5999 轮做线性拟合，看每 1000 轮的变化量：

| 指标                  | 每 1000 轮变化 | 判读       |
| ------------------- | ---------- | -------- |
| Mean reward         | +0.74      | 仍在改善，但很小 |
| Mean episode length | −0.69      | 基本持平     |
| 线速度跟踪误差             | +0.0006    | 已收敛      |
| 角速度跟踪误差             | −0.02      | 仍在改善，但很小 |
| 摔倒计数                | +0.005     | 已收敛      |

**结论：已经收敛，继续训练的边际收益很小。**&#x603B;分每千轮只涨 0.74，存活长度基本持平。

换句话说：**这 2 小时 26 分没有白花，但也没有必要再花第二个 2.5 小时在同一个配置上。**&#x4E0B;一步的收益不在"训练更久"，而在改配置（比如重新配比 4.4 里的头部/走路权重）或换任务（见第六章的进阶方向、真机验证）。

## 五、踩坑与经验总结

**经验一：官方源码 > 第三方封装**

封装镜像/一键脚本确实省事，但它有单点失效风险（比如镜像下架）。**真正可靠的是上游官方仓库**。把"依赖第三方"改成"自己走一遍官方流程"，初期多花 20 分钟，但永远不会被卡死。

**经验二：烟测是性价比最高的投资**

5 分钟的 `64 环境 × 5 轮` 烟测，能提前暴露 90% 的环境问题。**先跑通链路，再追求效果**——这个顺序不能颠倒。

**经验三：只看三个指标，不要被参数淹没**

训练日志会刷出几十个指标，新手很容易看懵。记住：**reward 涨 + 存活步数涨 + 摔倒计数跌 = 健康**。其余是给内行看的细节。

**经验四：reward 不能当成绩单用**

训练日志里的每个指标都有明确的**统计口径**（详见 4.2 的摔倒计数、4.5 的速度误差），不看口径直接读数，很容易得出完全相反的结论。而总分曲线会被课程加难扭曲——**复盘先看分项和行为指标，再看总分。**
